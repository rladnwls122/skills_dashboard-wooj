# 03 — 3장에 무엇을 어떻게 배분하는가

Type: prototype
Status: resolved
Blocked by: 01
Parent: ../map.md

## Question

탭은 `성능` / `트래픽` / `규칙 생성` 3장으로 확정됐다(map Notes 참조). `요약` 탭은 없애고, 대회 트래픽
2시간 동안 띄워두는 화면은 **`성능` 탭**이 맡는다. 지금 8장에 흩어져 있는 것을 이 셋에 배분한다.

`01`의 인벤토리를 놓고 정한다:

### `성능` 탭 — 상시 감시 화면

- **남길 지표와 접을 지표.** 한 장이 "지금 이상이 있는가"에 5초 안에 답해야 한다.
  남기는 쪽에 근거가 필요하다 — "이 숫자가 X를 넘으면 Y를 한다"를 못 쓰면 못 남긴다.
- **배치** — 무엇이 맨 위인가. 스크롤 없이 보이는 영역에 들어가야 하는 것은 무엇인가.
  상단 상태등 6칸(ALB/RDS/WAF/K8S/PODS/ANOM)을 유지할지, 줄일지, 없앨지.
- **지표 카드와 차트의 비율** — 어느 항목이 숫자 하나로 끝나고 어느 항목이 시계열을 갖는가.
  차트는 꺾은선으로 통일(확정), 툴팁은 시각(`HH:MM`)과 측정값 분리 표기(확정).
- **문구** — 카드 제목과 부제(`최근 3버킷 합계` 같은 설명)를 어디까지 줄일지.
  설명이 많아서 숫자를 못 찾는다는 게 불만의 일부다.
- 비용 패널(`05`)이 여기 올라오는지, 아니면 다른 탭인지.

### `트래픽` 탭 — 지금 뭐가 들어오고 있나

앱 요청 로그, WAF 차단 통계, 경로·IP·UA 분포, 이상 패턴 탐지. 기존 `로그`·`방화벽`의 통계 부분,
`점검` 탭의 내용이 여기로 접히는지 아니면 버려지는지 판단한다.

### `규칙 생성` 탭 — 그래서 뭘 막나

한 규칙의 일생(추천 → COUNT 적용 → 실측 → BLOCK 승격 → 롤백)이 이 한 화면에서 끝난다.
상세 흐름은 `04`가 정하므로, 여기서는 **자리만** 잡는다.

### 공통

- **드릴다운 경로** — `성능`에서 이상을 보면 어디로 가는가. 카드 확대(`⤢`)인가 탭 이동인가.
  탭 이동이면 컨텍스트(어느 경로/어느 시간대)가 따라가는가.
- **설정** — 톱니 모달로 뺀다(확정). 모달에 무엇이 들어가는지만 정한다
  (경기 시작 시각, 로그 그룹, 리소스 이름 강제 지정).

`/prototype`으로 러프한 레이아웃을 만들어 놓고 사람이 보고 고른다. 텍스트 와이어프레임이면 충분하고,
필요하면 실제 컴포넌트로 스텁을 만든다. 프로토타입 경로를 `## Answer`에 링크한다.

## Answer

와이어프레임은 아래에 인라인으로 둔다 — 별도 프로토타입 파일을 만들지 않았다. 배치가 `01`의 추천 판정에서
거의 그대로 굳었고, 확인이 필요한 건 "무엇이 스크롤 없이 보이는가" 한 가지뿐이라 텍스트로 충분했다.

번호는 `01`의 전수표 행 번호다.

### 확정 사항 요약

- **비용(노드 대수) 패널은 `성능` 탭 최상단, 채점 키 옆.** 가용성·성능 8줄과 노드 대수가 나란히 있어야
  "채점기 입력값 한 줄"이 된다. 패널 내용은 `05` 참조.
- **상단 상태등 6칸(#69)은 통째로 없앤다.** 색 하나로 답하는 장치이긴 하지만, 6칸이 지목하는
  곳(ALB/RDS/WAF/K8S/PODS)이 바로 아래 4타일·Node/Pod 개수와 같은 값이라 한 화면 안에서 두 번 읽힌다.
  이상 유무는 **채점 키 8줄과 이상 목록(#13)이 직접 답한다.** `buildSegments`도 같이 지운다.
- **드릴다운은 탭 이동 하나로 통일하고 카드 확대(`⤢`)는 폐기한다.** 확대는 같은 카드를 크게 볼 뿐
  다음 행동을 주지 않는다. 컨텍스트는 **시간창만 따라간다** — WindowBar가 이미 전역이라 공짜다.
  경로 컨텍스트는 넘기지 않는다(`트래픽` 탭에 경로 검색창이 이미 있다).
- **`점검` 탭은 폐기하되 프로브 자체(#58·#59)는 `규칙 생성` 탭 하단으로 옮겨 살린다.** 규칙을 올린 뒤
  정상 경로가 아직 200인지 확인하는 유일한 수단이라 롤백 판단에 필요하다(`04` 참조).
- **`로그` 탭은 `트래픽`으로 접힌다.** #53·#54·#55는 #57·#52와 중복이라 버린다.
- **갱신 주기는 셋으로 나뉜다.** 한 주기로 통일하지 않는다 — 값마다 움직이는 속도도 비용도 다르다.
  | 무엇 | 주기 | 왜 |
  |---|---|---|
  | k8s·CloudWatch 계열 (타일·Pod·Node·이벤트) | 기존대로 5초 폴링 / CW는 TTL 25초 | 이미 그렇게 돌고 있고 추가 비용이 없다 |
  | 노드 대수 패널 | 30초 (`05`) | `describe-instances`는 스캔 비용이 없다 |
  | 채점 키 8줄 (#21~#24) | **5분 자동** + `⟳` 수동 | 여기만 Insights 스캔 비용이 선형으로 붙는다 |

  채점 키를 1분으로 올리면 스캔 비용이 5배가 되는데, availability/performance는 5분 사이에
  판단이 뒤집힐 만큼 움직이지 않는다. 반대로 완전 수동으로 두면 대회 중에 누르는 걸 잊는다.
  `04`가 요구하는 **규칙 적용 전후 스냅샷 2회는 사건 기반**이라 이 주기와 무관하게 따로 돈다.
- **문구는 부제를 없앤다.** 카드마다 붙던 `조회 구간 …` `최근 3버킷 합계` 같은 설명 줄을 전부 지우고,
  창 정보는 WindowBar 한 곳에만 둔다(D10). 판단선이 필요한 카드는 제목 옆에 임계값 하나만 회색으로
  적는다(예: `Target 5XX  20/min`).

### `성능` 탭 — 2시간 띄워두는 화면

**남긴 것의 판단선** (못 쓰면 못 남긴다는 규칙을 통과한 것):

| 항목 | 넘으면 무엇을 하는가 |
|---|---|
| 채점 키 8줄 | availability 90% 미만 → 그 API의 replica. performance만 낮음 → 캐시·인덱스 |
| 노드 최종 평균 | 여유가 있으면 replica를 늘리고, 없으면 늘리기 전에 이 숫자가 얼마나 움직이는지 본다 |
| TRT | 0.5s 초과 → Pod/노드 CPU 확인. 2.0s + 200% → 즉시 스케일업 |
| 4XX | 50/min 초과 → `트래픽` 탭에서 404인지 403인지 가른다 |
| 5XX | 20/min 초과 → 앱 장애. 로그 → Pod → replica |
| RDS Client Conn | 80 초과 + TRT 동반 상승 → DB 병목, Pod를 늘려도 안 낫는다 |
| Node/Pod 현재=max | 상한이 병목 — max를 올린다 |
| 이상 목록 | CRITICAL 1건이라도 → 근거를 펼쳐 읽는다. **상태등을 없앴으므로 이 카드가 유일한 경보다** |

**접거나 버린 것**: 상태등 6칸(#69), RDS DB Conn(#5), WAF Allowed 단독(#7), Pod 건강 중복 3벌(#9·#12·#40),
Correlation·Timeline(#15·#16), Status Code 분포·상태코드 추이(#36·#37), 채점 키 개수·집계 구간(#18·#20),
탭 배지(#72), Insights 스캔량은 WindowBar 옆 한 줄로 축소(#17).

### `트래픽` 탭 — 지금 뭐가 들어오고 있나

```
 경로별 요청·차단 (#47, `의심` 배지)     |  QueryString 패턴 (#50)
─────────────────────────────────────────────────────────────────
 앱 요청 로그 (#57) — 기본 필터 4xx, 경로 검색
─────────────────────────────────────────────────────────────────
 Log Terminal (#52)                      |  Top Errors (#56)
─────────────────────────────────────────────────────────────────
 WAF Blocked / Allowed 추이 (#6·#7)
```

**경로별 통계에 `규칙 만들기` 버튼을 달지 않는다.** 경로 차단 규칙 자체를 버렸기 때문이다(`04`) —
미지정 경로는 ALB가 이미 404를 내므로 WAF가 손댈 이유가 없다. 경로 통계는 **감시용으로만** 남는다:
`의심` 배지가 붙은 경로가 보이면 그건 규칙을 만들 신호가 아니라 **그 경로가 진짜 404로 끝났는지
확인할 신호**다(#24 Exception Handling과 대조).

`트래픽` → `규칙 생성`의 통로는 **UA 목록**이다. `01`이 지적한 대로 `httpSummary.byUa`는 서버가
채우는데 UI에 없다 — 여기서 처음 노출한다. 스캐너·정찰 툴 UA 행에 `규칙 만들기` 버튼을 단다.

IP(#48)·Method(#49)·Header(#51)는 버린다. IP는 채점 부하생성기가 단일 IP라 판단선을 쓰면 채점 트래픽을
막고, Header는 정상 구성에서 영구히 비어 있다.

### `규칙 생성` 탭 — 한 규칙의 일생

자리만 잡는다. 흐름과 버튼 정의는 `04`.

```
 규칙 조립 2종 (#64 UA / #65 SQLi)   ← 경로 규칙(#63)은 폐기. 경로 AND 조건은 두 규칙 모두에 강제
─────────────────────────────────────────────────────────────────
 WebACL 규칙 목록 + WCU (#45·#46)  ← 각 행이 상태와 전이 버튼을 갖는다
                                     UA: 추천됨 → BLOCK  /  SQLi: 추천됨 → COUNT → BLOCK
─────────────────────────────────────────────────────────────────
 COUNT 실측 증거 (#42 샘플 원본 + 앱 로그 조인)  ← SQLi 규칙이 COUNT일 때만 펼쳐진다
─────────────────────────────────────────────────────────────────
 정상 경로 프로브 (#58·#59)  ← 규칙을 올린 직후 200인지, 아니면 내린다
```

### 설정 모달 (톱니)

환경 설정 10행(#67) + `.env 고정`(#68) + **경기 시작 시각**(신규, `05`가 요구). 그게 전부다.
