## Question

**전제 정정 (`01` 결과)**: 이 흐름은 기존 기능을 다듬는 게 아니라 **신규 구현**이다.
`UpdateWebACLCommand`가 `src/lib/server/waf.ts:7`에 import만 되어 있고 **호출되는 곳이 0건**이다.
README가 말하는 "적용·롤백"은 실제로 존재하지 않는다. `applyHistory()`/`waf_history`도 화면에 안 그려진다.
따라서 이 티켓은 상태 모델과 함께 **무엇을 처음부터 만들어야 하는지**도 정해야 한다.

로컬 WAF 시뮬레이터는 폐기한다(동작하지 않았고, COUNT 실측이 더 정확하다). 대신 **추천 → COUNT 적용 →
실측 확인 → BLOCK 승격**이 화면 위에서 어떻게 흘러야 하는지 정한다.

1. **승격 흐름의 상태 모델** — 규칙 하나가 가질 수 있는 상태는 무엇인가(추천됨 / COUNT 적용됨 /
   BLOCK 승격됨 / 롤백됨). 화면이 그 상태를 어디에 보여주는가. 상태 전이 버튼은 몇 개인가.
2. **COUNT 실측을 얼마나 봐야 승격해도 되는가** — 화면이 무엇을 보여주면 사람이 "안전하다"고
   판단할 수 있는가. 걸린 건수만으로는 부족하다 — 걸린 요청이 정상인지 비정상인지 구분되어야 한다.
3. **경로 스코프다운 강제** — `CONTEXT.md`대로, 차단 규칙은 제공 API 경로에만 걸려야 한다.
   미지정 경로를 Block하면 403이 나가서 요구사항(404)을 위반한다. 화면이 이걸
   ① 경고로 알려줄지 ② 아예 스코프다운 없는 규칙을 만들지 못하게 막을지.
4. **오탐 경보** — 정상 API 경로 요청이 403을 맞고 있는지를 무엇으로 세는가(WAF 로그의 action=BLOCK 중
   정상 패턴 요청? 앱 로그와의 대조?). 임계치는? 이 경보가 요약 탭에 올라가야 하는가.
5. **미지정 경로 404 감시** — 미지정 경로 요청이 실제로 404로 끝났는지를 어디서 읽는가.
   기존 `Exception Handling` 지표를 그대로 쓸지, 고칠지. WAF가 차단해버린 건은 앱 로그에 없다는
   기존 주의사항을 어떻게 화면에 유지할지.
6. **`규칙생성`(AI) 탭과 `방화벽` 탭의 관계** — 이 흐름이 한 탭에 다 들어가는가, 둘로 남는가.

`/grilling`으로 진행한다. 결정이 서면 `## Answer`에 상태 모델과 지표 정의를 적는다.

## Answer

### 0. 막는 대상은 UA와 SQLi 둘뿐이다 — 경로 규칙은 만들지 않는다

**미지정 경로는 ALB가 이미 404를 낸다.** WAF가 손댈 이유가 없고, 손대면 403이 나가서 오히려
요구사항을 위반한다. 그래서 `01`의 #63(`의심 경로` 규칙 조립)은 **폐기**한다.
경로별 통계(#47)는 감시용으로만 남는다 — `의심` 배지는 "규칙을 만들라"가 아니라
"그 경로가 진짜 404로 끝났는지 #24로 확인하라"는 신호로 뜻을 바꾼다.

남는 규칙은 **UA(#64)와 SQLi(#65) 둘**이다.

### 1. 상태 모델 — 진실의 원천은 WebACL, 경로는 규칙 종류마다 다르다

로컬 DB에 상태 컬럼을 두지 않는다. 규칙의 상태는 **`GetWebACL` 응답에서 매번 파생**한다.
자체 상태 테이블을 두면 사람이 콘솔에서 직접 만진 순간 화면이 거짓말을 하고, 대회 중에는
그 거짓말을 알아챌 방법이 없다.

| 상태 | 판정 근거 | 화면 표시 |
|---|---|---|
| `추천됨` | WebACL 규칙 목록에 이름이 없다 | 회색. 조립된 JSON만 있는 상태 |
| `COUNT` | 규칙이 있고 `Action.Count` | 노랑 + 매칭 건수 (**SQLi 규칙만 이 상태를 가진다**) |
| `BLOCK` | 규칙이 있고 `Action.Block` | 빨강 + 차단 건수 |
| `내려감` | 한 번 올라갔다가 지금은 목록에 없다 (`waf_history`에 기록이 있는데 WebACL에 없음) | 회색 취소선 |

**COUNT 단계는 SQLi에만 있다.**

- **UA 규칙**: `추천됨` → `BLOCK` → `내려감`. 버튼 2개(`BLOCK으로 올리기` / `내리기`).
  관측된 UA 문자열에서 조립되므로 무엇을 막는지 사람이 눈으로 이미 확인한 상태다.
  COUNT를 한 번 거치면 그만큼 늦게 막힌다.
- **SQLi 규칙**: `추천됨` → `COUNT` → `BLOCK` → `내려감`. 버튼 3개(`COUNT로 올리기` /
  `BLOCK으로 승격` / `내리기`). 관측과 무관한 **고정 시그니처 세트**라 우리 앱의 정상 쿼리가
  거기 걸릴지 아무도 모른다. 실측 없이 올리면 정상 요청을 403으로 잘라 가용성 점수를 깎는다.

`내리기`는 어느 상태에서든 같은 버튼이고, 롤백과 철회를 구분하지 않는다 —
누르는 사람 입장에서 하는 일이 같다.

**모든 버튼은 사람이 누른다.** 자동 승격도 자동 롤백도 없다(map 원칙).

> UA를 COUNT 없이 바로 막기로 한 대가는 **오탐이 실측이 아니라 사후에 드러난다**는 것이다.
> 그래서 4의 프로브 확인이 UA 규칙에서는 선택이 아니라 필수 절차다.

### 2. 승격 게이트 — 걸린 건수 + 그게 정상이었는지 (SQLi 규칙 전용)

COUNT 상태의 SQLi 규칙 행을 펼치면 두 숫자와 한 표가 나온다. UA 규칙에는 이 절이 뜨지 않는다.

- **매칭 건수** — `07`의 결론대로 `action` 필드가 아니라 **`nonTerminatingMatchingRules`**에서 센다.
  COUNT 매칭은 `action`이 `ALLOW`로 찍히므로 `action`으로 세면 0건이 나온다.
- **정상/비정상 분해** — 매칭된 요청의 `requestid`를 앱 로그와 조인해(`07`) 응답 상태·지연을 붙인다.
  - 앱에서 **2xx로 정상 처리된 요청이 하나라도 있으면 그건 오탐 후보**다. 승격 버튼을 누르기 전에
    그 행을 보라는 뜻이고, 이게 "걸린 건수만으로는 부족하다"에 대한 답이다.
  - **조인 불가 건수를 반드시 같이 적는다.** `07`대로 POST/PUT은 양쪽 다 `requestid`가 없어 조인이
    안 된다. `매칭 34건 (정상 0 · 비정상 21 · 조인 불가 13)`처럼 셋을 나란히 쓴다.
    조인 불가를 "비정상"에 합치면 화면이 없는 근거를 지어내는 것이 된다.

**승격 판단선**: 매칭 20건 이상이 쌓였고 그중 앱 2xx가 0건이면 안전하다. 20건 미만이면 버튼은
누를 수 있게 두되 `표본 부족` 회색 문구를 붙인다 — 2시간짜리 대회에서 표본을 기다리다 못 막는 것이
더 큰 손해라, 막지는 않고 알리기만 한다.

### 3. 경로 스코프다운 — 강제한다 (② 선택)

**경로 차단 규칙은 안 만들지만, 경로 스코프다운은 남는다.** 둘은 별개다 —
전자는 "경로 자체를 막는 규칙", 후자는 "UA/SQLi 규칙이 걸리는 범위를 제공 API 경로로 좁히는 것"이다.

WAF는 ALB **앞**에 있다. 스코프다운을 빼면 미지정 경로로 들어온 악성 UA 요청이 ALB의 404에
닿기도 전에 WAF에서 403으로 잘린다. `Exception Handling`(#24)이 그만큼 깎인다.

**스코프다운 없는 규칙은 아예 만들 수 없다.** 경고 배너는 채택하지 않았다.

- 조립기(`ruleassemble.ts`)가 내놓는 UA·SQLi 규칙은 `AND(제공 API 경로 조건, 탐지 조건)` 형태로만
  나온다. 경로 조건이 비면 조립 버튼 자체가 비활성이다.
- 손으로 붙여넣은 JSON을 올리는 경로에도 같은 검사를 건다 — 최상위 `Statement`가 `AndStatement`이고
  그 자식 중 하나가 제공 API 경로에 대한 `ByteMatchStatement`/`RegexPatternSetReferenceStatement`가
  아니면 `COUNT로 올리기`가 거부된다.
- 이유는 `CONTEXT.md` 그대로다. 미지정 경로를 WAF가 Block하면 403이 나가고, 요구사항은 404다.
  그러면 채점의 `Exception Handling`이 깨진다. 이건 취향이 아니라 신뢰 경계 검증이라 우회로를 두지 않는다.

### 4. 오탐 경보 — 승격 전후 availability 델타로 센다

"WAF BLOCK 중 정상 패턴 요청"을 세는 방식은 쓰지 않는다. 무엇이 정상 패턴인지를 화면이 다시 정의해야
하고, 그 정의가 틀리면 경보 자체가 틀린다. 대신 **이미 채점기와 같은 정의를 쓰는 숫자**를 쓴다.

- **규칙을 올리는 버튼(UA `BLOCK`, SQLi `COUNT`·`BLOCK`)을 누르는 순간 채점 키 8줄(#21~#24)의 값을
  스냅샷으로 남긴다**(`waf_history`에 저장).
- 그 후 5분간, 어느 키든 availability가 스냅샷보다 **1%p 이상 떨어지면** 오탐 경보다.
- **1차 확인선은 정상 경로 프로브(#58·#59)다.** 규칙을 올린 직후 정상 비율이 100%가 아니면 즉시
  경보다. 프로브는 Insights 스캔이 없어 공짜고 즉시 답이 나온다. **UA 규칙은 COUNT를 안 거치므로
  이 확인이 유일한 즉시 신호다** — 올린 뒤 프로브를 한 번 돌리는 것을 절차로 못박는다.

**경보가 뜨는 자리는 두 곳이다.**

`03`이 상단 상태등 6칸(#69)을 통째로 없앴으므로 상태등에는 올리지 않는다. 대신:

1. **`규칙 생성` 탭의 해당 규칙 행** — 빨갛게 되고 `내리기` 버튼이 강조된다. 방금 올린 사람이 보는 화면.
2. **`성능` 탭의 이상 목록(#13)** — `detectAnomalies()`에 규칙 하나를 더한다:
   `최근 5분 내 규칙 적용 이력이 있고 어느 채점 키가 스냅샷 대비 1%p 이상 하락` → `CRITICAL`.
   근거 줄에 규칙 이름과 하락한 키를 적는다. 탭을 옮겨 놓고 있어도 알아챌 수 있는 자리다.

이상 목록은 이미 `waf_history`를 볼 이유가 없던 순수 계산 함수였다. 이 규칙 하나 때문에 입력이
하나 늘어난다 — 대신 `buildSegments`를 손댈 필요가 없어진다(어차피 `03`이 지운다).

### 5. 미지정 경로 404 감시 — 기존 지표를 그대로 쓴다

`Exception Handling`(#24, 서비스 경로 밖 요청 중 `status = 404 or 403` 비율)을 고치지 않고 쓴다.
채점기와 같은 정의라 우리가 다시 정의할 이유가 없다.

기존 주의사항 — **WAF가 차단한 건은 앱 로그에 없으므로 이 비율에 잡히지 않는다** — 는 지표 옆
한 줄로 유지한다. 다만 경로 규칙을 아예 안 만들고(0) 스코프다운을 강제하면(3) 미지정 경로는
**어떤 경우에도 WAF에 걸리지 않는다.** 그러므로 이 지표가 100% 미만이면 원인은 WAF가 아니라
ALB/게이트웨이 설정이다. 그 문장을 지표 옆에 그대로 적어둔다 — 대회 중에 엉뚱한 데를 뒤지지 않게.

### 6. 탭 관계 — 하나로 합친다

`방화벽` 탭은 없앤다. 통계(경로·쿼리스트링 분포)는 `트래픽`으로, 규칙의 일생 전부는 `규칙 생성` 한 탭으로
간다. 규칙 목록·WCU(#45·#46)가 지금 `방화벽`에 있는데, 그게 규칙 상태를 보여주는 유일한 곳이라
`규칙 생성`으로 옮기지 않으면 흐름이 두 탭으로 쪼개진다.

### 처음부터 만들어야 하는 것

`01`이 확인한 대로 승격·롤백 기계는 코드에 **없다**. 새로 쓸 것은 다음이 전부다.

| 만들 것 | 자리 | 비고 |
|---|---|---|
| `setRuleAction(ruleJson, action \| null)` | `server/waf.ts` | `GetWebACL` → `LockToken` → 규칙 배열 갱신 → `UpdateWebACL`. 승격·적용·내리기가 전부 이 함수 하나다. `action: null`이 제거. `WAFOptimisticLockException`이면 재조회 후 1회 재시도 |
| 스코프다운 검사기 | `server/ruleassemble.ts` | 위 함수의 진입 조건. 조립 경로와 붙여넣기 경로가 같은 함수를 통과한다 |
| `updateWafRuleAction` | `actions/dashboard.ts` | 서버 액션 1개. 성공 시 `insertWafHistory`에 채점 키 스냅샷 동봉 |
| COUNT 실측 병합 | 신규 모듈 | `07`의 2단 쿼리 — WAF 로그에서 `nonTerminatingMatchingRules` 매칭분의 `requestid` 목록 → 앱 로그 2차 쿼리 → 코드에서 병합. **SQLi 규칙 하나를 위한 것**이라 범위가 좁다 |
| 오탐 이상 규칙 | `server/anomaly.ts` | `detectAnomalies()`에 규칙 1개 추가 + 입력에 `waf_history` 추가. 승격 후 5분 내 채점 키 −1%p → `CRITICAL` |

**안 만드는 것**: 경로 규칙 조립(#63) — `assembleRule("path", …)`과 그 테스트를 지운다.
`buildSegments`(상태등 판정) — `03`이 상태등을 없앴다. UA 규칙용 승격 게이트 — COUNT를 안 거친다.

**되살릴 것**: `insertWafHistory`/`getWafHistory`/`waf_history` 테이블은 이미 있고 호출만 없다.
지우지 말고 여기에 연결한다. `applyHistory()`와 `WafPanel.history`도 이 흐름의 이력 표시로 살아난다.

**지울 것**: `UpdateWebACLCommand`와 함께 import만 되어 있는 `CheckCapacityCommand`는 쓰지 않는다.
WCU는 `GetWebACL` 응답의 `Capacity`로 이미 보이므로 조립 전에 사람이 눈으로 확인하면 된다.
